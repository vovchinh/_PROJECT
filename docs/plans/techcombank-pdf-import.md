## CURRENT FINDINGS

- The existing path is **Thu Chi → Nhập sao kê** in [`src/pages.jsx`](../../src/pages.jsx), with the importer in [`src/features/BankStatementImport.jsx`](../../src/features/BankStatementImport.jsx). The importer accepts `.xlsx` only. [`src/lib/bank-statement-file.js`](../../src/lib/bank-statement-file.js) reads and normalizes Excel locally (5 MB/5,000-row limits, browser SHA-256), mapping a date, description, debit/credit or signed amount, and optional reference.
- [`src/forms.jsx`](../../src/forms.jsx) owns the current Thu Chi form. It creates/edits a **draft** through `create_cash`; owner/manager posts with `post_cash`. Posted cash is corrected by dated reversal/replacement, not raw editing. The existing form must be reused for complete PDF-row review.
- `public.cash_transactions` is the voucher, `public.cash_movements` is the **only** cash ledger, and `public.cash_category_snapshots` freezes the selected category at posting. There is no separate `finance_transactions` table. Sources: [`001_core.sql`](../../supabase/migrations/001_core.sql), [`014_expense_categories.sql`](../../supabase/migrations/014_expense_categories.sql), [`015_document_corrections.sql`](../../supabase/migrations/015_document_corrections.sql).
- `public.expense_categories` is the existing Nhóm thu chi catalog for both directions, with `category_kind` and `profit_eligible`. `public.cash_accounts` holds workspace accounts and confirmed opening balances; it has **no bank-account-number field**. A bank credit is not automatically revenue, and a bank debit is not automatically operating expense. Purchase receipts affect stock; sales events affect revenue/COGS; payroll approval recognizes salary expense, while payroll/advance cash vouchers affect the existing cash ledger. A PDF row must not create a duplicate business effect.
- [`016_bank_statement_import.sql`](../../supabase/migrations/016_bank_statement_import.sql) already has workspace-scoped batches and rows, `stage_bank_statement`, `classify_bank_statement_row`, `get_bank_statement_import`, and `confirm_bank_statement_rows`. Staging has no ledger effect. Confirmation is atomic, owner/manager-only, audited and request-idempotent; it creates a voucher and calls `post_cash` for each selected row. Staff can stage/classify; viewer can read staged rows. The current UI stages **only valid** parsed rows, while invalid rows remain in the local preview.
- Existing duplicate hints compare the current batch with posted/manual cash using date, direction, amount, description or reference. They do not inspect other *pending* batches or establish a verified link to sales, purchases, payroll or COD documents. The same file SHA-256 with a different parse payload is rejected, so a future parser revision needs an explicit, non-destructive strategy.
- Privacy is a gate: migration 016 grants all workspace members read access to bank batches and raw staging rows, whereas migration 019 restricts HR-linked cash from staff/viewer. PDF staging must not disclose salary or other sensitive transaction descriptions through the older bank read path. The local 017–020 HR migrations exist in the worktree; their installation on the real Supabase project is unverified.
- The 019 cash/ledger/audit visibility guard identifies only vouchers actually linked to HR payroll or salary advances. A PDF-derived salary payment posted as an unlinked bank voucher is still visible to staff/viewer; the report wrapper also detects only HR-linked cash. Protecting staging alone would therefore be insufficient.
- Phase 1 baseline: `npm run test:bank-statement` **12/12 PASS**; `npm run test -- src/lib/bank-statement-file.test.js` **6/6 PASS**. These use synthetic Excel/JSON fixtures and do not test this PDF or a real Supabase deployment.

## EXISTING THU CHI MODEL

“Required” distinguishes a draft from a posted voucher. UI limits are not always database constraints; PDF import must follow the stricter reviewed contract rather than bypassing the form silently.

| Field | Type | Required? | Source | Validation | Posting effect | Editability |
|---|---|---|---|---|---|---|
| `id`, `workspace_id` | UUID | System | Server/current workspace | Workspace-scoped FK and RPC role check | Links voucher to movement/audit | Stable; never user-edit |
| `account_id` | UUID | At post | Existing `cash_accounts`, user selects | Same workspace; opening balance/date confirmed; transaction not before opening | Copied to cash movement | Draft only |
| `direction` | `in`/`out` | Always | User; PDF debit/credit suggestion | Table constraint; category must match direction at post | Sets movement sign | Draft only |
| `transaction_date` | Date | At post | User; PDF transaction date suggestion | Finite actual date, not before account opening | Movement business date | Draft only |
| `date_estimated` | Boolean | Always; must be false at post | User confirmation | Posting rejects estimated date | Gates posting, no movement column | Draft only |
| `category` | Text code | At post | Existing `expense_categories` chosen by user | Active category in workspace with matching direction | Frozen in movement and `cash_category_snapshots`; profit policy comes from category | Draft only |

| `status` | `draft`/`posted`/`reversed`/`deleted` | System | Trusted commands | Allowed transitions; `deleted` is a tombstoned draft | Post/reversal creates immutable movement rows | Never raw-edit after post |

The visible form fields are `direction`, `transaction_date`, `description`, `account_id`, `category`, `amount`, `date_estimated`, and `notes`. `post_cash` requires owner/manager, an actual date, an opened account and an active same-direction category. `reverse_document` is owner-only and appends a compensating movement; [`015_document_corrections.sql`](../../supabase/migrations/015_document_corrections.sql) can also create a linked replacement draft.

None of the PDF columns below has been verified against the supplied PDF yet.

## PRIVACY ALLOWLIST

Only transaction date, optionally necessary posting date, transaction description, debit/credit and normalized integer VND amount, direction, bank transaction reference (if present), necessary currency, source page/row, parser warning/status/confidence, and an optional local SHA-256 fingerprint may leave the local parser **after the user continues**. The selected ERP `account_id` and category are application data, not extracted PDF identities. Keep only the transaction description needed for the business voucher; do not append unrelated table/page text. The original PDF stays local by default; it is not uploaded, stored in Supabase Storage, sent to OCR/AI, or logged. A neutral generated source label replaces the original filename. `raw_row` must be constructed from this allowlist only, never from an entire PDF line/page.

Reading PDF bytes/text transiently in local memory is technically necessary for extraction; discard nontransaction material promptly. No raw PDF text or complete transaction descriptions in production diagnostics. If a page is scanned or has an unusable text layer, flag it locally as unsupported/OCR-required; cloud OCR requires a separate explicit privacy/architecture decision.

## PARSER STRATEGY

At Phase 1, only the sample's existence was checked. Phase 2 observations below supersede that initial uncertainty for this **one** sample, without establishing production parser support. A separate image excerpt elsewhere in the repo is not proof of this PDF's layout or issuing-bank format.

For the later `TechcombankStatementAdapter`, propose local PDF text extraction with [Mozilla PDF.js](https://mozilla.github.io/pdf.js/examples/index.html). Its documented page API and [text items with strings and transforms](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html#~TextItem) permit page-aware, position-aware analysis. Phase 2 should inspect **only transaction-table structure**, redact examples, detect text-layer quality, and record multiple layout variants before implementing `canParse`/`parseTransactions`/`normalizeTransaction`/`validateTransaction`. Avoid a single fixed coordinate template: detect headers, group positioned tokens into lines/columns, join multiline descriptions until the next transaction anchor, ignore repeated headers/footers, and preserve page/row references. Use existing `parseBankDate`/`parseBankAmount` rules where applicable; server must revalidate normalized values. Scanned/image-only pages are not silently OCR'd or sent to a cloud service.

## SECURITY RISKS

1. **Accidental PDF upload/PII retention:** file input must remain local through preview; never send bytes, full page text, full account number, account holder/profile or original filename. Sanitize `raw_row` and diagnostics.
2. **Current read-path mismatch:** 016 viewer/member reads of bank rows can reveal transaction descriptions, including salary rows otherwise hidden by 019. Resolve access policy before server staging PDF data.
   The same review must include posted cash, movements, category snapshots, audit events and `get_workspace_report`: 019 restricts only vouchers linked to HR tables, and 016 bank audit details can contain a client-supplied source label or duplicate-review reason.
3. **Malformed PDF/parser abuse:** bound bytes/pages/text-items/time/memory; reject encryption/malformed text or unsupported scans without partial financial effects. No arbitrary embedded-script/external-resource execution.
4. **Tampered browser payload:** 016 validates amount/date/category/account at server, but cannot verify normalized values against PDF bytes it never receives. Treat browser hash as a dedupe hint, require human comparison/confirmation, and never describe it as cryptographic source attestation.
5. **Duplicate imports/retries:** same-file SHA, row identity, pending/posted cross-batch checks, immutable outcomes and request IDs must prevent double posting. Possible duplicates stay reviewable; linked/skip outcomes create no new movement.
6. **Workspace/document isolation:** every candidate account, category and linked document must be checked server-side in the current workspace; keep composite FKs/RLS and actor audit.
7. **Financial classification:** debit/credit affect cash only. Category and linked-document decisions must not create another sale, stock receipt, payroll expense or COD revenue.
8. **Sensitive local sample:** the PDF is untracked and now ignored by an exact `.gitignore` rule. Do not attach it to issues, commit it, or copy it into test fixtures. A generated source label must replace its filename before staging.

## PHASE 2 — LOCAL SAMPLE FORMAT ANALYSIS

**Method and boundary.** PDF.js inspected the file locally in memory. Diagnostics emitted only page geometry, text-item counts, column positions, date/amount **patterns** and reconciliation counts; they did not emit PDF text, descriptions, account-holder data, account numbers, references or monetary values. The PDF was not uploaded or copied into a fixture. This analysis is evidence for a parser design, not a working import or a proof that every Techcombank statement shares this layout.

| Observation | Redacted evidence and consequence |
|---|---|
| Text layer and geometry | All 8 pages have selectable text. The displayed pages are landscape at approximately 840 × 595 points, while raw text transforms are rotated 90°. A parser must normalize each item's transform through the page viewport before grouping rows. Naive raw-X/raw-Y grouping produced false headers and dates. No OCR is needed for this sample. |
| Two table sections | Pages 1–6 use one grid; pages 7–8 use a second grid with a new header on page 7 and a different row pitch. Page 6 includes nontransaction material after its last candidate row. The format detector must be section-aware, not one fixed template for the whole PDF. |
| Candidate rows | Geometric date anchors yield 5, 17, 17, 17, 17, 10, 7 and 5 candidates by page (95 total). These are **not** 95 validated transactions. The first grid has 83 candidates; the second has 12. |
| First grid, pages 1–6 | Dates appear as `dd/mm/yyyy`; amount tokens use comma grouping. Each candidate has one debit-or-credit movement and a running-balance cell. All 82 adjacent running-balance deltas reconcile with the signed movement in the in-memory check. Some descriptions continue for 1–3 additional lines. This supports a candidate extraction rule but does not verify every field's meaning or every row's business validity. Running balances remain outside the upload/staging allowlist. |
| Second grid, pages 7–8 | There are two numeric cells per candidate that have equal absolute values and opposite signs in all 12 rows. Neither behaves as a running balance (0 of 11 adjacent deltas reconcile). **Quarantine this section** as unsupported/needs human format verification; do not silently call either cell debit/credit, post these rows or count them as imported transactions. |
| Page continuation | A transaction header is present at the start of each section, but pages 2–5 and 8 continue rows without repeating it. Parser state must carry a verified section layout across page breaks and stop at nontransaction material. |
| Unverified fields | No separate posting/effective date, transaction-reference rule, currency label or ERP bank-account mapping has been established from this analysis. Do not fill those fields by assumption. An ERP cash account must be confirmed per table section, without importing a full bank-account number. |

**Parser decision.** Detect the sample's text layer and page rotation first; then identify a supported section by its verified header and geometry. Group date-anchored rows in display coordinates, join continuation text only inside the transaction cell, and validate one nonzero movement side plus allowed money/date formats. Use a transient balance check only as a local consistency signal; never include balance in normalized rows, diagnostics or server payload. Preserve warnings and page/row references. An unknown header, changed column geometry, missing amount/date, or the pages 7–8 layout must produce a review/unsupported outcome with **zero** staging or ledger effect. Build synthetic, redacted fixtures containing decoy personal data to prove it cannot leave the parser; do not commit the real PDF as a fixture.

**Privacy gate before server staging.** For PDF rows, owner/manager-only access is the conservative policy until product roles are specified and tested. An additive server path must enforce the PDF field allowlist, neutral source label and protected read access; the existing 016 `raw_row` and `source_name` checks are not enough. Test the whole route through staging, posted cash, cash movements, category snapshots, audit and reports. A server-controlled PDF source marker is needed if the existing Excel workflow retains wider access. A browser-supplied hash or source label cannot establish that marker.
